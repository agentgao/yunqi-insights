两种研发生产范式：人推动流程 vs Task 驱动交付

02:25:24 — 02:29:03 官网回放 ↗
蔡何
02:25:25

我们作为业务域的研发或者技术负责人，可能都有类似的经历，就是我们的需求堆积量可能会很多，然后 bug list 列表越来越多，我们的研发任务可能已经完成了，但是实际交付还没有彻底上线，其原因可能是还在等待部署，等待测试，等待验证。其实我们现在已经有很好的 AI 工具辅助我们做这些事情了，但是整体交付质量仍然没有得到彻底的端到端提升。其原因就是，现在仍然还处于一种智能辅助人的阶段。

02:26:03

那它会带来三个方面的问题。第一个方面就是，仍然以人完整地推动这个流程作为核心。这就好比我们作为一种家庭式作坊，高级研发工程师是我们的作坊主，他需要带领一堆 Agent，或者他下面的同学，去完成一些任务。这些任务需要他去组织、安排，每一个任务完成之后，需要他再往下推进。这样，整体效率其实都会浪费在整个上下文的传递、衔接、推动上面。所以这是第一个最主要的问题。

02:26:40

第二个就是，AI 加速的还是一个局部工序。比如说整个研发链路要分成很多环节，我们可能会有 DBA 的一些部署，DBA 的一些运维，以及我们测试端到端的这个验证等等。这些环节，其实我们可能把 Coding Agent 用得非常好了，但是这些环节可能还没有像 coding 一样被同等对待。所以这个过程的一些衔接等待时间也会非常长。第三个就是，由于是家庭作坊式的模式，所以最终的需求交付质量和任务交付质量严重依赖于人的精力和经验，尤其是人的精力，因为 AI 时代，准确说，任务执行的成本非常低，但是我们人的精力却变得非常宝贵，因为你要做更多的决策、更多的判断。

02:27:33

所以在这种模式下，本质上就是一种低效的、原始的家庭作坊式生产模式。我们要怎样才能让人的精力和注意力彻底解放，让任务能够自主交付呢？我们认为至少要满足三个基础的条件。第一个就是，我们研发的整个端到端流程是清晰、可以被定义的，每个环节应该让数字人参与什么、人参与什么、怎么协作，是可以被定义的，然后由一套整体的编排和调度系统把它组织起来。第二个就是，人的个人经验应该被转换为生产的标准模式。

02:28:08

我们人的个人经验，包括高级研发工程师，或者你们的运维人员、测试人员，他应该把经验用 Skill、Plugin 以及相应的工具，变成各个岗位数字人应该拥有的标准生产知识，沉淀下来，让数字人有据可依、有法可依地执行。第三个就是，每个环节、每个岗位交接的产物和交接的要求应该是标准化的。这个节点应该产出什么、交接什么、怎么样才能算通过，应该可以被清晰定义，这样，每个节点、每一个数字人之间，才可以清晰地进行流转。

02:28:47

这就是从家庭作坊式变成具有标准、具有明确分工的自主推动模式。所以，个人效率只有进入到完整的生产系统里面，我们才能把整个组织的交付能力提升。

幻灯片 04

Agentic SDLC：让 Task 成为组织交付主线

02:29:03 — 02:30:13 官网回放 ↗
蔡何
02:29:04

这就是我们讲的 Agentic SDLC，让整个任务成为我们组织交付的主线，然后通过整体的流水线编排，将数字人、人的协作分工，统一编排进去。然后我们再通过相应的工程约束规范，把我们的经验沉淀到整个系统编排流程里面，再通过一些强约束的gate policy 和证据链去保障交付质量，最终达成端到端完整交付。当一个需求和任务被提出的时候，它可以自主地从生产到研发到测试到部署，最后到上线前的决策、证据提交，让人彻底解放整个链路中被分散的注意力。

02:29:49

这里就引出我们的 AutoWonder。AutoWonder 平台是我们阿里云开放平台内部围绕自主交付这个目标打造的一个 AI native 实践平台。它可以将人、我们的任务、所有的产物和证据，完整地组织编排在一起。我们所有自主交付的经验和沉淀，都可以在这个平台中体现。

幻灯片 05

AutoWonder：把人、数字人和工具组织在一起

02:30:15

我们来看一下这样一个平台，它是怎么组织生产的。我们的团队以及团队成员可以在平台上定义各个岗位的数字人以及他的职责，然后配置好相应的工作权限范围、工具、知识库、技能等等。然后再定义清晰的编排流程、流水线，包括人在里面应该怎样协作。把它清晰地定义出来之后，整个平台流程就可以完全自动化地运转，人员也可以通过这样的方式协作。右侧是一个真实执行的 group graph，这个 graph 里面可以看到任务推进到哪里，数字人怎么执行、怎么决策，人怎么参与的，每一个环节都可以被清晰地看到，可被追溯、可被管理。

02:31:05

幻灯片 06

三端协作：同一 Task，人在熟悉入口参与

蔡何
02:31:23

既然我们建立了这样一套完整的编排流水线，人和数字人都被编排在一起了，那我们人该怎么去参与到这里面的协作呢？有三个常见的模式，这也是呼应我们说，人的注意力应该集中在自己更擅长和更熟悉的地方。第一个就是工作群，我们日常工作最多的应该就是工作群，或者钉钉，或者我们的微信、飞书等等。我们可以把数字人同等对待。比如说一个流水线上的这些工人，你可以把他们拉到我们的群里边，让他跟我们一起参与讨论、参与聊天，最后需求确认之后，让他自动去推动这个任务的完成。

02:32:00

当任务需要决策的时候，又通过相应的 IM 工具主动通知、反馈给决策人，让人在需要确认的地方去确认。第二个就是我们的个人 Agent，个人 Agent 是我们现在日常用得非常多的。我们可以将个人 Agent 连接到团队整个交付的流水线上面。所以当我们需要任务的发起、查询、管理的时候，同样可以通过个人 Agent，在端侧维护和管理。然后是原始的工单平台，工单平台本质上就是任务的入口，所以工单平台同样承载了所有执行和管理的角色。

02:32:41

无论以什么样的入口，本质上我们都是围绕同一个任务作为事实，它们都共享了统一的目标、状态，还有产物以及证据。所以在这种模式下，我们人其实可以，以前比较分散的一些模式，以及以前分散的管理模式，完全可以被收纳到统一的产物层面上，不需要我们反复的去转移和提交上下文。

幻灯片 12

自主交付之后：效率持续优化

02:38:47 — 02:40:14 官网回放 ↗
蔡何
02:38:48

当我们整个平台能力，或者交付能力的效率和成本，都能得到极大的提升的时候，我们还在想，是不是说我们的效率还可以被优化？那我们该怎么做呢？第一个就是数字人应该越用越聪明，我们平台将自动进行数字人的记忆和自迭代的一些优化，它可以把规则、事实、遇到的坑点沉淀成可复用的记忆，防止下一次再踩坑，少一次 Loop，可能就会少大量的 Token。反复执行、反复错误的一些地方，把它变成我们相应的可用的记忆，下一次避开。

02:39:27

第二个就是整个流水线，其实是面向单个数字人的，它的优化不能完全决定整个流水线的效率。所以整个流水线自进化的效率也需要被持续提升。我们每一次的运行、每一次的交互，所有的证据链，人、模型执行、Agent 执行的这些思考，都会被我们平台沉淀。每一次的执行都成为我们优化、自进化的依据。比如说 Token 的消耗，是不是有反复的 Loop。比如说有一些依赖工具没有安装，是不是可以首次安装，后续减少反复安装。

02:40:04

通过这些机制，让流水线每运行一次任务，就让它成为下一次交付的一些优化证据。
