AI 原生前端研发工作流：共享 Demo、全栈开发与自主缺陷修复

02:08:15 — 02:24:54 · 黄宗权

黄宗权以需求设计、需求开发和缺陷修复三个连续场景，说明如何从 Coding Copilot 走向端到端 Autopilot。设计阶段让产品、设计与前端围绕同一可运行 Demo 协作并提前收集用户反馈；开发阶段补齐工具、知识与产品级工作空间，通过需求路径、Agent Browser 和 A11Y 优化做自动验证修复。缺陷阶段以浏览器插件采集页面、网络及代码位置上下文，推动 Agent 自动认领、修复、部署验收和提交证据丰富的 CR，再按评审评论继续优化。

  • 只加速编码无法同等加速需求交付，需要覆盖设计、开发和缺陷修复全流程
  • 共享可运行Demo及产品交互规范减少重复制作、跨角色信息转换和后续返工
  • 产品级工作空间打通前后端工程、真实后端请求和配套MCP/CLI/Skills
  • 将Spec拆成用户操作路径作为测试用例，以Agent Browser及A11Y优化完成validate/fix闭环
  • 插件补齐缺陷上下文并定位前端代码，Agent自动修复后将原因、过程与验收证据随CR上报
  • 任务认领由人转向Agent，人在评审中关注质量判断并通过评论继续驱动优化

幻灯片 02

AI 编程突飞猛进，需求交付速度却没有同等地飞跃？

02:08:49 — 02:09:40 官网回放 ↗
黄宗权
02:08:49

那么首先我们为什么要对研发流程做升级呢？过去一年，AI 编码的能力可以说是突飞猛进，我们的需求交付速度也在提升，但是远没有 AI 编码的能力进步这么大。为什么会有这个差距呢？因为写代码只是需求交付过程中的一个部分。如果我们仅对编码环节做提效，需求的端到端交付速度肯定没有办法获得同等幅度的提升。为了进一步提升我们的需求交付速度，我们也对 Agent 做了升级，从 Coding Copilot 升级为 Autopilot，让我们的 Agent 从辅助编码走向端到端的需求交付。

02:09:33

接下来我将结合三个具体的场景，聊一聊我们是怎么做的。

幻灯片 03

前端研发的三个 AI 实践

02:09:40 — 02:09:49 官网回放 ↗
黄宗权
02:09:42

这三个场景分别是需求设计、需求开发和缺陷修复。那我们先来聊需求设计。

幻灯片 04

AI 生成原型很快，需求设计仍耗费大量人的时间

02:09:49 — 02:11:31 官网回放 ↗
黄宗权
02:09:51

现在让 AI 生成一个原型可以说非常快了，但是在我们实际工作当中，需求设计仍然会耗费我们大量的时间。我们统计下来主要分两点，首先是重复制作，对我们的产品经理来说，他的大多数需求其实是做线上已有功能的迭代，而不是要从 0 到 1 做一个新的产品。AI 非常擅长做从 0 到 1 的 Demo 生成，但是我们的产品经理却要先把线上已有的功能做一次还原，然后再去表达这一次要迭代和调整的内容是什么，那很多时间就会花在线上已有功能的调整上。

02:10:36

对于我们的产品经理来说，我们大多数产品的交互视觉规范已经很成熟了，但是他还是需要重复制作这些设计稿。然后我们再聊这个协作沟通上的问题。同一个需求，我们产品经理是用原型来表达的，而设计师是用交互稿和视觉稿来呈现的，前端再用视图层代码去做一次实现。同一个信息在不同阶段之间、不同载体上做一次转换。每一次转换都有可能发生信息的偏差或者理解的偏差。

02:11:18

如果说需求有一些反复的调整，设计师、产品经理、研发还需要去做反复的沟通和对齐。那这两个问题我们是怎么解决的呢？

幻灯片 05

让所有角色，围绕同一份可运行 Demo 协作

02:11:31 — 02:13:06 官网回放 ↗
黄宗权
02:11:32

我们在内部搭建了一个 UX 平台，这个平台的核心思路很简单，就是让产品经理、前端和设计师围绕同一份可运行的 Demo来去进行协作。产品经理在完成需求描述之后，我们的 UX Agent 会基于我们现有的前端工程，follow 这个产品的交互视觉规范，去完成 Demo 的开发。因此，这个 Demo 默认就是符合我们产品的交互视觉规范的。所以设计师也只需要对它做一些局部的优化和调整，可以把时间集中在更加需要设计师做专业判断和设计品味输出的地方。

02:12:20

在产品设计方案评审完成之后，我们前端也不需要再做视觉还原了。因为我们的产品经理和设计师已经用 UX Agent 完成了这个前端视图层的代码，我们只需要直接复用就可以。这也很好地解决了 Agent 做视觉还原很难做到百分百的问题。更加重要的是，我们可以把这一份高保真、可运行的 Demo 提前发给用户去体验，提前收集用户体验上的一些反馈，来及时调整我们的产品设计方案，避免后续开发过程中再做返工。

02:13:01

我们聊这些概念可能不是很直观，

幻灯片 09

UX 平台如何让 Agent 基于现有产品工作？

02:14:05 — 02:15:14 官网回放 ↗
黄宗权
02:14:08

我们从底向上看，底部是一个产品级的工作空间，每一个产品的接入方都需要提供、维护这个产品级工作空间，要提供前端工程、组件库、交互视觉规范，以及这个产品的测试账号。我们平台会在沙箱环境，用这个测试账号完成自动化登录，然后去保存 Cookie 信息。然后前端工程发起的这些接口请求，我们就可以携带这个 Cookie 信息转发到真实的后端接口里，从而让这个前端工程可以真的跑起来。

02:14:51

中间我们的 UX Agent 就是跑在这个产品级的工作空间。最上面我们的 UX 平台会提供通用的实时预览、圈选评论、Demo 发布这些功能，让我们不同的角色可以在同一份可运行的 Demo 里面，进行迭代设计和体验反馈。

幻灯片 10

设计结果，既能提前验证，也能直接进入开发

02:15:14 — 02:15:35 官网回放 ↗
黄宗权
02:15:15

有了这个 UX 平台，我们减少了重复制作的时间，以及避免了沟通协作。同时也可以提前拿到用户的反馈，避免后续返工。在产品设计方案明确了之后，接下来我们再看一下是怎么做需求开发的。

幻灯片 11

AI 编程能力突飞猛进，需求开发却离不开大量人工参与

02:15:35 — 02:16:48 官网回放 ↗
黄宗权
02:15:36

在需求开发上，我们也是从人的耗时出发，统计出了三类最耗时的问题。第一类问题呢，是如果我们给到 Agent 的 AI 工具不够完备，我们人就可能要接手做一些研发上的操作。那同样的，如果我们给到 Agent 的知识不够完备，Agent 就会高频触发一些 human in the loop，让我们做一些低质量的一些决策。第二个问题是跨角色、跨工程的协作沟通问题。

02:16:09

典型的就是前后端要高频地做一些接口约定和联调。如果需求有一些变更，前后端还需要反复对接接口的变化和各自的进展。第三个问题呢，是 Agent 的交付质量。如果说不够高，人就需要花很多时间和 Agent 沟通，怎么去做迭代和优化。而 Agent 的交付质量很大程度上取决于 AI 的验证能力。那我们要怎么去提升 AI 的验证能力？好，接下来我们看一下这三个问题的解决方案。

幻灯片 12

面向 Agent 的产品级研发环境

02:16:48 — 02:18:54 官网回放 ↗
黄宗权
02:16:49

我们还是从底向上看，底部是我们提供的一个 AI Harness友好的环境。一方面，我们要给 Agent 补齐可以调用的 AI 工具，提供配套的 MCP、CLI 以及配套的 Skills，教会 Agent 去用这些工具。另一方面，我们也要不断完备我们的知识，避免这些不必要的 human in the loop。左上角是我们的产品级工作空间，这个工作空间我们在UX 平台里面也提到过，在需求开发环节会继续复用。

02:17:28

在这个工作空间内，我们会声明所有的前端工程和后端工程，描述每个工程的职责作用，以及它们之间的依赖关系。另外，我们前端和后端也要各自维护好自己工程的 Harness 环境。然后我们的 Agent 在这样的一个壳工程内，就可以实现跨工程、跨前后端的全栈端到端开发了。这样也避免了前后端频繁沟通协作的时间。然后我们再看端到端验证。为了提升验证的覆盖率，我们首先会把需求的Spec 形式化地拆分成不同用户的操作路径。

02:18:16

每个用户的操作路径就是一份 Markdown 文件。同时，它也是我们的一个端到端测试用例。AI 会使用 Agent Browser 来执行这个用例文件。另一方面，为了提升 Agent Browser 验证的成功率，我们也会做一些 A11Y 的优化，让 Agent 在开发期间，就把 A11Y 做好。然后 AI 会在这个环节完成一个 validate 和 fix 的 Loop。

02:18:48

直到所有的问题被修复完成，所有的测试用例执行成功。

幻灯片 13

人工耗时更少，交付质量更高

02:18:54 — 02:19:24 官网回放 ↗
黄宗权
02:18:55

有了这样的一个产品级壳工程，我们减少了人工接手的时间，减少了前后端联调沟通的时间，也提升了交付质量。

02:19:11

那么当我们在验收 Agent 交付的功能的过程中，我们可能又会新发现一些问题。那么这些问题我们要怎么去做修复呢？

幻灯片 14

AI 修前端 Bug 已经很快，前端 Bug 数量却未显著降低

02:19:24 — 02:20:52 官网回放 ↗
黄宗权
02:19:27

在缺陷修复环节，我们也观察到了一个现象。很多 bug，AI 已经修得非常快了，但是我们积压的 bug 数量却没有明显降低。那我们也是分析下来，主要有三个不同的原因。第一个原因呢是我们之前的 bug fix 还是靠人工去推动的。如果我们一段时间比较忙，bug fix 的事情可能就会不断往后推。第二个问题呢是 bug 的上下文不足。我们有很多 bug 都是这种一句话的缺陷，或者说这个 bug 里只有一张截图。

02:20:08

那我们熟悉这个产品的研发，可能看到这张图，我们就可能凭经验来判断它的复现方式是什么，它的问题是什么，修复的预期又是什么。但是 Agent 是很难做到这点的。第三个问题呢是，如果 Agent 把这个 bug 修好了，然后我们收到 Agent 提交的 CR，我们是真的敢合并吗？如果说我们还是需要手工把 Agent 提交的分支部署到预发环境，然后再做一次手工的端到端验证，那还是会耗费大量时间。

02:20:50

这 3 个问题我们是怎么解决的呢？

幻灯片 15

缺陷修复的 Autopilot 方案

02:20:52 — 02:23:08 官网回放 ↗
黄宗权
02:20:53

针对刚才提到的问题一，我们很自然地会把 bug fix 的认领和推动从人转变成 Agent。这样，当我们提交完一个 bug 之后，我们的 Agent 就会自动扫描到这个 bug，然后开始修复。针对刚才提到的上下文问题，我们也开发了一款浏览器插件。那我们可以用这个插件来去上报 bug。插件会自动采集页面上有问题的元素、页面链接、相关的网络请求和报错信息，来给到 Agent 充分的 bug fix 上下文信息。

02:21:34

此外，我们也用 React Fiber 的相关原理，可以让插件在解析到元素之后，直接获得这个元素对应的前端代码位置，告诉 Agent 出问题的前端工程是什么，它的文件在哪里，代码在第几行。这样 Agent 就可以又准又快地完成修复。针对刚才提到的问题三，我们也复用之前提到的产品级壳工程。AI 在完成修复之后，可以把它的分支部署到我们的预发测试环境，然后让 Agent 去做一次端到端的验收。

02:22:14

然后把它定位到的原因、修复的思路、修复的内容、验收的过程和结果，统一跟随着这个 CR 一起上报。这样我们看到这份 CR 之后，就可以快速做出判断：我们能不能合并。另外，我们在合并 CR 的过程中，也进一步发现了一些问题。有一些 bug，AI 确实修好了，我们还是觉得可以进一步优化。比方说我们觉得 AI 修的文案，或者它的样式还不够完美。这个我们也是仿照人的工作流。

02:22:53

如果我们在这个 CR 上提交一些评论，让它继续优化，这个 Agent 也会继续修复。然后再去更新这个 CR。那也是讲这些概念可能不是很直观。

从需求设计到缺陷修复，贯通研发链路
