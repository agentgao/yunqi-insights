00:37:33

首先我们看一下 Agent 的输入。其实 Agent 在执行过程中会看到很多的信息，比如说系统策略，就比如各个模型厂商系统策略， 还有我们自己的系统提示词，以及已经授权的用户给 Agent 输入的一些 prompt。最后我们的 Agent 它还会执行各种工具， 比如说进行网页搜索、读邮件或者调 API，拿到 API 的结果。这些数据它都会进入模型的上下文，但从系统的角度来说，它们的权威性完全不一样。

00:38:47

00:39:38

如何确保 Agent 在长程任务中不偏离原始目标？

00:40:12 — 00:41:40 官网回放 ↗
蒋航
00:40:13

然后解决了目标来源的问题，下一个问题就是在 Agent 执行过程中，尤其是长任务，其实模型可能会不断的进行规划，然后也可能进行一些上下文的压缩。在这个过程里面，其实目标或者说我们针对这个目标的终止条件，它已经慢慢的丢失了。那么这个时候怎么去防止 Agent 丢失了这些信息呢？其实我们是把整个目标做了一个持久化的存储，也就是我们这里的已授权的目标状态，它是一个持久化的状态，这里面就包含刚才提到的目标范围、成功条件，以及当前的版本。

00:40:50

在一些关键的节点，我们会针对这个状态进行持续的对账。比如说上下文压缩的时候， 或者模型重新规划的时候，或者说外部的环境已经发生了改变， 以及模型要去执行一些高危操作。在对账的时候，我们会看当前任务的状态，以及我们预期已经保存的这个状态，它是否一致？比如说任务有没有完成，是否已经偏离目标了。如果偏离了，那我们就需要去重新处理。就这个对账，它会返回三个结果：第一个就是继续，也就是说我没有偏离目标；第二个如果偏离目标了，就是重新规划；第三个是权限发生了变化，我就要去进行重新授权。

00:41:31

这里的思路总结成一句话，就是我们的目标需要持久化的保存，而执行过程需要持续去进行一个对账。

我们解决了目标偏离的问题，其实还有一个问题就是，虽然我当前生成的计划是符合用户的目标，但是这个计划它执行的动作不一定取得了用户的授权。如果每一次工具调用都需要让用户去授权，那么用户很快就会审批疲劳。就比如一个 Coding Agent，他们的分析报告就显示，93%的审批其实都是权限审批，而 Saber 的分析发现，其实在这些权限审批里面，只有14%~18%的这些操作会真正影响我们的业务系统。

00:45:19

00:45:59

所以其实这里的核心思路就是说，我们需要先限定单次影响的爆炸半径，然后再由模型能力的提升去不断的提升我们影响的一个可靠性。就是通过这种隔离的边界来保证我们模型即使有幻觉，即使出问题了，它的损失也是我们可接受的。

如何让 Agent 使用凭证而不持有凭证？

00:46:19 — 00:48:07 官网回放 ↗
蒋航
00:46:19

好，再下一个就是凭证的问题。其实我们通常在传统应用里面会把凭证放在环境变量或者配置文件里面。但这个行为在 Agent 里面就非常不可取，风险非常高。因为 Agent 它可能会编写代码， 而这个代码它就可以去读我们的环境变量，甚至处理我们的文件。用户他就可以通过自己的指令来诱导我们的 Agent 来获取环境变量里面的凭证，然后把这个凭证甚至外发出去。

00:46:48

而且一个非常危险的事情是， 我们环境变量里面这些凭证，它可能脱离了我们 Agent 的执行环境，还能够继续使用。所以这个凭证泄露是一个非常危险的事情。那么如何解决这个凭证泄露的问题呢？所以我们划定了三个服务域，就首先是 Agent 执行，它的 Runtime 和工具执行是不可信执行域，在这个不可信执行域里面，我们不能够持有凭证，那么不持有凭证我怎么去访问？

00:47:15

就所有 Sandbox 里面的工具调用，我们都要经过工具网关。工具网关先做一次上下文的绑定，就绑定说我这一次操作是我某一个工具，某一个身份发起执行的。然后再到我们的策略执行点，这个策略执行点是我们可以在工具网关之后去判断我这一个工具它到底能够执行哪些操作。比如说我们可以在这里去限定它只能做一些写操作，或者只能做一些读操作，不能够做删除操作。

00:47:43

最后就是和凭证非常相关的，我们会有一个代签服务，这个代签服务它去真正从我们凭证服务里面拿到凭证，然后做一个代签名，最终通过这个签名好的数据来向云 API 发起一个请求。这样的话，在不可信的这个 Runtime 里面，Agent 就完全拿不到任何凭证了。
