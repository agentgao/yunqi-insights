Terraform Autopilot Workflow：从客户工单到数字人自主交付

02:41:49 — 02:57:28 · 陈汉璋

陈汉璋介绍阿里云 Terraform Provider 随资源规模增长面临的迭代、适配与回归压力，说明为什么仅有 AI 编码辅助仍受制于人的流转和兜底。报告以真实客户需求单展示基于 AutoWonder 的 Task、业务 Workflow 和平台底座三层结构，追踪 API 文档缺失、Terraform 语义适配和测试资源不足三个阻塞点及人工恢复过程。最后区分计划内发布决策与预期外异常，把领域知识、工具及环境断点补齐为基础设施，使研发人员逐步转为流程建设者与管理者。

  • Terraform Provider将声明式配置转为云OpenAPI编排，规模扩大同时增加功能与回归维护压力
  • 交付主体从人转向数字人后，过去由研发串联的知识、平台调用与异常恢复断点集中暴露
  • 同一需求Task保存上下文，业务Workflow定义流程，AutoWonder底座提供调度、工具、环境和恢复
  • 真实ADB PostgreSQL需求展示文档、API特性适配和测试环境问题如何在同一工单中协作处理
  • 区分必须人工授权的计划内发布节点与可通过知识、文档或环境改进消除的异常介入
  • 研发职能由具体执行转向Workflow建设、管理与持续改进，交付吞吐量仍有提升空间

幻灯片 06

从真实需求出发 - 什么是Terraform

02:43:11 — 02:44:25 官网回放 ↗
陈汉璋
02:43:12

首先简单介绍一下 Terraform，我们在部署新的应用服务的时候，通常需要给这个应用服务准备基础设施。比如准备网络、服务器或者数据库。在过去，我们可能需要人工去控制台上创建，或通过 OpenAPI 调用方式管理云上基础设施。有 Terraform 之后，我们其实只需要写一段声明式配置脚本。把这段配置文件交给 Terraform，它就会自动调用云上的 OpenAPI，为我们创建云上的资源和基础设施。

02:43:49

这里的一个核心是，用户不需要关心底下 OpenAPI 是怎么调用、怎么编排的，只需要描述我们想要的云上基础设施长什么样子，Terraform Provider 就会自动编排调用这些 OpenAPI，来帮助客户管理云上的资源，降低云资源管理成本。我们团队主要的工作之一就是不断维护阿里云的 Terraform Provider，不断迭代它的产品功能，以支持阿里云最新的产品能力，满足客户的需求。

幻灯片 07

从真实需求出发 - 十年演进与交付压力

02:44:25 — 02:45:36 官网回放 ↗
陈汉璋
02:44:25

阿里云的 Terraform 从 2017 年到现在，大概支持了将近 1200 个资源。随着资源越来越多，我们面临的研发压力也越来越大。因为一方面，阿里云也在不断推出新的产品、新的功能能力，我们需要让 Terraform 很快、很及时地去支持这些产品能力。另外一方面，对于存量已经发布的这些资源，我们也需要不断迭代。因为存量产品也会继续演进、新增功能，此时我们要不断迭代存量资源，补齐属性，以及适配 API 本身的一些变更。

02:45:03

同时我们整个研发过程还要做完整的回归测试。那么资源越多，整个回归测试的压力也是越大。遇到问题之后我们要及时去修复。所以，当我们面对的产品规模越来越大之后，我们整个团队的研发压力也越来越大。因此 Terraform 这个业务，我们需要找到一条更加可行的自主交付的路径。这就是我们的一个背景。

幻灯片 08

当数字人开始接单 - 一张需求单的旅程

02:45:36 — 02:46:35 官网回放 ↗
陈汉璋
02:45:36

我们可以看一下，在过去，在传统的开发模式下，当客户提出一张需求单之后，整个需求单从提出到最后交付的链条都会经过哪些过程？首先我们需要对需求做一些分析，了解当前实际情况，以及用户真实意图，对需求做一些澄清，查证现状，以及 OpenAPI 的能力和约束。之后我们要根据具体情况，分析这个产品功能要怎么在 Terraform 侧实现、支持上。可以看到，整条交付链路非常长，并且涉及到多个存量系统。

02:46:15

过去这个交付可以一直平稳运行，是因为我们的研发会把一个个平台跟系统串在一起，主动推进这张需求单的流转，让它最终可以交付到客户现场。

幻灯片 09

当数字人开始接单 - 距离端到端交付还差什么

02:46:35 — 02:49:30 官网回放 ↗
陈汉璋
02:46:35

这种交付方式其实就是图上面的这个情况，在传统研发模式下，是人持有这个需求单，人作为需求的负责主体。当有了 AI 之后，我们可以用 AI 做一些辅助分析，查证一些背景，帮助我们更快地分析、澄清需求。以及在中间，比如做编码开发的时候，AI 现在也可以直接生成代码，去帮我们做一些测试验证以及评审。但是这种开发模式，其实人是最大的兜底机制，人也是最大的瓶颈。

02:47:15

系统整个需求交付吞吐量的瓶颈，就在于研发团队本身有多少。如果我们能够把交付主体从人转向数字人的话，因为数字人很容易横向扩充，今天可能只有几个数字人，明天我们可以很快速地扩容，让更多的数字人进来去帮我们消化存量需求。理论上，当我们的交付主体从人变成数字人之后，我们的吞吐量会有一个成倍的提升。但是事情没有那么简单。当我们把数字人放入真实的业务场景之中，我们发现它能帮我们推进一个个具体任务，但是我们人还是要在里边不断引导、参与、纠正它，我们才能把一张需求从头到尾做完。

02:48:05

例如，在推进需求理解的时候，它需要知道 Terraform 是什么，需要知道一些领域知识，知道这张需求提出来的背景，以及约束和当前的进展。同时，对于刚刚提到的非常多的存量平台系统，这些存量平台系统过去是为人打造的，今天数字人如果想直接用它，其实没有那么简单。存量这些系统，我们还需要做一些适配，提供一些 CLI 工具或 MCP 工具，让数字人能够自主调度这些平台能力，来实现这一张需求单。

02:48:40

最后，因为数字人在一些场景下可能会陷入异常，这里边有可能是运行时本身的异常，也有可能是它在推进某个需求的时候，因为缺乏某些上下文或背景信息，导致无法判断、无法决策，这时候，必要时是应该转人工的。也就是说，我们的期望很美好，希望把交付主体从人变成数字人。但在实际落地过程中，我们发现当交付主体变成数字人之后，过去我们研发一直接住的这些系统断点，现在就浮现出来了。我们需要补齐这些断点，把它们变成基础能力、基础设施。

02:49:23

这也是我们通过 AutoWonder 平台重构 Workflow 最重要的出发点。

幻灯片 10

Workflow 支撑数字人推进整张需求

02:49:30 — 02:51:02 官网回放 ↗
陈汉璋
02:49:31

接下来我介绍一下 Terraform 的 Workflow 是怎么构成的。我们可以把这个系统分成 3 层，最上层是需求任务 Task。对于每一张客户的需求单，我们都对应到某一个具体的AutoWonder 任务。同一张需求单就会有同一个上下文以及背景信息。不同的数字人就可以基于同一个背景信息很好地工作、合作、协作。中间这里是我们 Workflow 的主体，对应到每一个具体业务，它的编排流程可能会有差异。

02:50:11

比如一开始，刚刚另外一个同事分享的前端的，他的 Workflow 跟 Terraform Workflow 可能就不太一样。对于大家各自业务中 Workflow 的定义，也需要根据自己的业务做相应调整。最底下这个 Workflow 底座就是 AutoWonder，它会为整个 Workflow 提供任务调度、上下文管理、工具和环境准备，以及一些异常处理，必要时通过一些渠道将人 involve 进来，去参与、去介入，去恢复这个异常。

02:50:47

我们最终的目标就是说，这一张需求单能够被不同的数字人持续自主地推进，直到形成一个可验证、可交付的结果，然后最终再产出、再转给人。

幻灯片 11

为数字人重构 Workflow - 真实交付案例

02:51:02 — 02:53:36 官网回放 ↗
陈汉璋
02:51:03

我们可以拿一个真实的客户需求单，简单分享一下，我们真实场景下，用 AutoWonder 结合 Terraform 的 Workflow，是怎么去工作的。这个客户提出来一个诉求，是希望用 Terraform 能够管理 ADB、PostgreSQL 的一个产品形态。这张需求单从提出到最后交付，其实不到三天。但是这三天一波三折，中间有各种问题。

02:51:35

比如在查证和澄清阶段，数字人阅读了这张需求单的背景，并且去查阅了 API 文档。它发现 API 文档当前并没有描述相关信息，也就是说 API 文档本身不足以支撑我们把 Terraform 做接入。此时数字人就把这个问题在同一张需求单上抛出来，并且转交给相应的产品方，让产品方进行协作。产品方把一些关键信息补齐之后，AutoWonder 会重新把这个数字人恢复起来，继续往下推进。

02:52:14

在中间的实现环节，实践过程中，我们数字人在真实地写Terraform 代码、做编排调用的时候，发现 API 本身的一些功能形态跟 Terraform 的一些特性不太一致，会导致 Terraform 有异常。这个时候，数字人因为之前缺乏这一方面的领域知识，就无法自主判断下一步应该怎么做、怎么做适配。这个时候，它也是在同一张需求单上，把需求单转给 Terraform 研发。

02:52:45

Terraform 研发介入之后，根据具体情况设计兼容适配的方案，再把这个需求单流转回数字人，由数字人继续往下实现、推进和验证。到最后测试环节，其实也遇到一些异常情况，就是我们测试区的资源不足。这导致数字人无法交付一个可验证、可信的结果。这时候也是人参与进来，帮助它协调资源。结合这个具体案例，我们可以看到，整个交付过程，其实人还是介入很多。

02:53:22

但是所有事情都发生在同一张需求单上面，每一个环节耗时多少，每一个环节因为什么原因阻塞住，每一个节点到底下一次应不应该出现人工介入情况，我们就可以统计出来了。

幻灯片 12

为数字人重构 Workflow - Human In The Loop

02:53:36 — 02:55:15 官网回放 ↗
陈汉璋
02:53:38

这里我想表达的是，我们在基于 AutoWonder 也好，或基于其他同类产品，构建我们自己业务的 Workflow 的时候，一定会出现一种情况，就是一开始人的介入还是非常多。这里面人的介入可以分成两类，一类是计划内的决策，这一类主要是指，比如我们这个产品或功能最终要发布上线前，这一个发布节点必须由人确定，由人授权，这个动作是我们预期内的决策。

02:54:15

哪些是属于异常呢？比如刚刚那一张需求单的解决，在一开始分析需求背景和 API 能力的时候，发现 API 文档存在异常，存在信息缺失。这一部分其实属于预期外的，因为我们应该联动产品以及文档团队，把我们的 OpenAPI 文档做得更好，数字人下次就不会在这里卡住了。再比如刚刚在具体的编程实现过程中，它测出来 API的形态跟 Terraform 本身预期的结果不太一致。

02:54:51

那这一类的信息缺失是因为他缺乏领域知识。导致它无法自主决策、判断往下走。这一部分也是属于预期外的异常。这部分工作，我们就需要在下一轮通过 AutoWonder 也好，通过自主补齐这个 Workflow 里面的知识库，让下一轮需求单进来之后，数字人能很好地工作。

幻灯片 13

为数字人重构 Workflow - 需求交付与工程产出

02:55:15 — 02:56:17 官网回放 ↗
陈汉璋
02:55:16

不断迭代这个 Workflow，我们最终在一个统计周期内也看到一个结果，就是面向客户需求的交付吞吐量提升了 300%，我们的代码工程产出也有 3 倍、3.5 倍的增长。这个数字其实说明，我们当前的 Workflow 以及数字人已经参与进我们真实客户的交付节奏里边了。但其实跟我预期内的可能还不太一样，因为我们预期，比如当前 Terraform 存量工单有数千个，我们很希望能够在很快的时间，几周，一个月或半年内都解决掉。

02:55:55

但是现在这个吞吐量显然还不足以满足我们的需求。但我相信，随着 Workflow 本身不断迭代，因为我们在不断补齐它的能力，它的技能也好、知识库也好、工具也好，这个 Workflow 会像一个飞轮一样，不断越转越快，最终我们才能很好地满足客户需求。

幻灯片 14

为数字人重构 Workflow - 研发职能的转变

02:56:17 — 02:57:27 官网回放 ↗
陈汉璋
02:56:18

最后谈一下，我对 AI 时代下工程研发职能转变的思考。在过去，我们每一个研发或者每一个具体的人，其实在整个业务交付链路中是具体的执行者。我们要自己亲力亲为做需求分析、做研发实现，也要做测试验证和最后发布，或跟不同产品方做沟通协作，我们人的精力其实就耗在这种执行的工作里边。当现在有了基于 AutoWonder 构建的数字人自主交付的 Workflow 之后，人的职能就转变成了流程的建设者和管理者。

02:57:05

我们可以从一项项具体任务里面抽身出来。我们可以更好地设计、迭代这个 Workflow 本身，并且有更多的时间和精力，去思考怎么引导我们的业务走向更符合客户预期的方向，更好地服务客户。这就是我今天最后的分享，感谢大家。
