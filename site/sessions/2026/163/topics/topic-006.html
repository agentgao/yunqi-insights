企业级 Agent 工程实践：决策增强、质量评估与经验自演进

01:43:15 — 02:08:15 · 罗寒曦

罗寒曦讨论在无法消除模型不确定性的前提下如何设计企业 Agent。报告以智能客服和 AIOps 为例，把输入与执行边界、上下文分层导航、简单可验证的 Loop 和文件契约、安全护栏及决策留痕组合为决策增强架构；通过覆盖率、执行完成度、红线与用例验证评价效果。面对上线后的复杂工单和大量 bad case，进一步提出从观测轨迹挖掘知识、沉淀结构化与非结构化经验，并在任务开始、工具调用前、出错时和交付前召回验证的自演进闭环。

  • 模型幻觉、输入歧义、知识时效、重试污染与静默失败，需要通过架构边界和可观测性控制
  • 上下文工程以分层路由、渐进式披露和知识召回缓解全量知识与有限上下文的矛盾
  • Loop应是轻量、质量可控的工作流运行时，通过文件契约和状态机验证阶段交接
  • 决策留痕保存目标、推理依据、数据源选择和执行判定，为归因与自演进提供基础
  • 质量评估强调覆盖、完成度、通过率及禁止行为，架构与评估共同促进客服交付
  • 经验可表达为YAML、SOP、Skill或RAG知识，并在四个关键时机注入上下文

幻灯片 05

可靠性改进 - 不是让模型更准，而是给模型限定边界

01:45:25 — 01:47:24 官网回放 ↗
罗寒曦
01:45:26

通常我们一个团队要去做企业 Agent 的 开发，就是最直觉性的做法，非常合理。首先挑一个最强的模型，我 们配好极致优化的提示词，给它加载一个 RAG，把知识灌进去，然后再给它搭配一个 ReAct 的 loop循环，让它自己实现工具的调用。然后我们就可以开始去做一些 这种单例测试和 Demo 演示了。当然这个效果也会非常好， 95% 左右的这个准确率，回答的又准确又像人。

01:45:58

但是一旦真正的把它要运用到生 产环境下，各种问题就接踵而来。比如模型的幻觉导致模型已读乱回，不受控地一股脑跑下去。比如说越权问题、风险操作，模型就一把梭哈跟你执行到底。然后还有一些，比如说像 Agent 记忆衰退的问题，就是任务跑着跑着它就不知道自己在干什么了，等等这些问题。那么这些问题，我们看起来觉得还是模型问题，但是等等，我还是想带着大家去深入地梳理一下。

01:46:37

模型幻觉是模型的固有属性。大模型推理的这个过程啊，本质上就 是根据我们的权重， Temperature，Top K 的激活的一次概率采样的一个过程。所以我们输入一个固定的 提示词，在不同的上下文，在不同的重试阶段，它输出的 Token 必然是不同的，这不是缺陷。这是大模型的一个固有问题，我们是没有办法去消除它的。所以今天我给大家带来的第一个结论，如 果我们要去做 Agent 的可靠性的改进，不是去让模型变得更准确，而是要给模型限定好边界。

01:47:19

那么我们为什么会给大家这个结论呢？那首先我们来看一下。

企业Agent决策失误因素 - 输入不确定

罗寒曦
01:47:25

造成 Agent 决策失误的因素有哪些？首先在 Agent 输入层，输入就是代表我们给 Agent 挂的 RAG的知识，我们给 Agent 设定 的 role 角色的一个提示词，以及用户对 Agent 发布的这些任 务，这些我们都把它定义成输入。输入层就有六大类不确定性的来源。我们举一个具体例子，比如说我 给模型设定的一个 role 角色。

01:47:50

我们的提示词就可能存在一个歧义性。那用户给 Agent 去下发任务，他 的这个说法或者提示词的这个方式也是五花八门。另外就是我们给 Agent 挂的 RAG 知识库，知识库本身就有时效的问题，对吧？那么所以这些因素都会造成我们的 Agent 在开始的时候就可能产生决策失败。

幻灯片 07

企业Agent决策失误因素 - 长链路误差放大

01:48:14 — 01:49:10 官网回放 ↗
罗寒曦
01:48:13

那么出现决策问题以后， 我们通常性的做法就是。不停地去重试、复现问题，然后再去解决。这个是我们传统软件工程的一个做法。但是在企业 Agent 的生产环境 下，特别是在一些长程任务，就是长链路的任务下，我们去重试不一定有效果。为什么？因为重试本质就是在已经执行错误的执行轨迹上，再去添加一层不确定性。我们可能这次重试修了这个问题，但是这个上下文环境已经污染了。

01:48:50

我们修完这个问题的同时，可能会引入新的不确定性。然后在长程任务的这个背景 下，单次任务的不确定性经过多链路、多条任务的这个多执 行路径的这个累加产生复利，就会将整个 Agent 决策的成功概率拉得非常低。

幻灯片 08

企业Agent决策失误因素 - 无约束边界

01:49:10 — 01:49:57 官网回放 ↗
罗寒曦
01:49:11

那出现了这些决策失误以后， 我们可能还要再问一下自己，我们有没有办法能够观测到这类的失误。我们要知道大模型其实有个非常非常危险的问题，它叫做静默失败。静默失败的意思就是模型它可能 不会主动告诉你模型它出错了，而是它一股脑地将错就错，一直执行到底，直到最后给你一个牛头不对马嘴的答案。那出现这类问题的时候，我们的 Agent 的 基础设施里面有没有对应的这个兜底方案？

01:49:46

有没有对应的降级方案？如果没有，那么就代表是我们的 这个 Agent 是没有边界约束的，那么这就是决策失误的第三个原因。

企业Agent工程实践 - 决策增强架构（智能客服案例）

01:51:22 — 01:53:22 官网回放 ↗
罗寒曦
01:51:21

那么这么听起来可能有点虚，我们结 合实际的案例来看一下具体怎么去做。这个是我们在过去两年做的智能客服的案例。我们在这个智能客服上我们 上了一套决策增强型框架。这个框架主要分成三大块内 容，第一块就是上下文工程，负责去管理我们的知识经验，以及 在合适的时候负责这个经验召回。第二大块就是 planning、execution、reflection，也就是我们的 ReAct 循环。

01:51:52

那么在这层呢，它的主要功能 就负责输出结构化的强契约，来严格地限定我们在执行链路上每一个步骤的边界。然后最后根据我们的 reflection 反思，将结果重新注入到上下文来驱动我 们这个 loop 循环的下一轮迭代。然后侧边这一块呢是我们的第三大块安全护栏。安全护栏是贯穿于我们整个链条里面，全程负责去做前置的合规安全审计，还有风险识别，以及在执行过程中高风险的 Human-in-the-loop 风控。

01:52:32

那么在这三大层之间呢，我们还有 一条暗线，这个暗线叫做决策留痕。决策留痕的意思，就是说我的大模型在推理或者执行每一步链路过程中，它必须要把它这个决策的 过程和决策判定的依据要全部记录下来。也就是说从目标到中间推理，到数据源 的选择，到执行，到我们置信度的判定。全程要把它的决策依据记录下来。并且这个决策的这个依据后面是 作为我们 Agent 可观测能力，以及我们 Agent 自进化、自演进的关键数据地基。

01:53:13

好，那么我们从这个架构 层，我们再继续去深挖，看看我们每一部分在设计的过程中，到底遇到过哪些问题，

企业Agent工程实践 - 上下文工程

罗寒曦
01:53:22

然后我们是怎么解决的。首先我们从上下文工程开始讲起。在上下文工程中，我们遇到的第一 个矛盾就是全量知识和我们有限的上下文的 context 的这个空间上的一个矛盾。我们如果把全量的知识注入到我 们的模型的 context 上下文中，就必然会出现一个上下文 频繁压缩的这么一个情况，结果就会导致我们的 Agent 的记忆的退化。那么一个解法就是我们可以人为 的去设定好我们整个这个提示词，整个经验去注入上下文的过程，就是靠人为去管理着我们的模型的记忆。

01:54:02

但是在这个里面我们投入的人力的成本 会直接抹掉我们 AI 这边拿到的收益。还有一条路，就是我们在去年做的一个尝试，让 Agent 沿着长链路的任务链条，自己去发现，找到路由，去加载我们的 经验，做这个知识召回。在这条链路上，我们总结了四个设计原则，就分别是渐进式披露、单一原则。引用而非复制，文件系统即路由。那这四个原则怎么去理解啊？我们举例，还是以智慧客服的案例来举例。

01:54:44

我们在这个任务识别和分类的 过程中，我们设计了三级路由，分别是根导航、域导航和知识图谱。那么在根导航、域导航、知识图谱之间，它们自己会有严格的职责限制。比如说像根导航，我们只会去注入我 们的这个全局的规则和一个目录地图，它只做这一件事情。它的提示规模大概就是在 200 行左右，大于 200 行的话我们该下放的下放。那么在域导航，在这里我们会根据客户画像，还有客户的这个意图分类，然后把它。

01:55:20

转到我们对应要解决什么样的问题上。然后最后导航到第三步，导航到知识图谱。我们再根据我们前面的这个 路由和导航的这个路径啊，去判定我们到底是要解决什么产品的问题？这个产品的这个解决方案是什么？再把这类的知识图谱召回到我们的这 个大模型的上下文中，然后执行这个。整个的这个处理。所以我们可以做个形象的比喻 啊，上下文是我们 Agent 运行的一个燃料，燃料好不好直接决定着我们 Agent 这个发动机是不是能够正常的或者有效的运行下去。

企业Agent工程实践 - 智能体Loop方案

01:56:01 — 01:58:14 官网回放 ↗
罗寒曦
01:56:00

好，那接下来我们来讲讲这个发动机， 也就是我们智能体的这个 Loop 的方案。那么在 Loop 方案这个执行过程中， 大家可能会有一个固有的一个认知啊。Loop 其实就是通过我们一个 Harness 的手段，去把模型的智慧化程度给提升。但是根据我们过去两年的这个 实践经验来看， Loop 和 AI的关系可能没有我们想象中的那么强。Loop 的这个设计，它的一个 考量啊，其实更多的应该是根据我们实际 Agent 的应用场 景和我们 Agent 的这个架构。

01:56:39

设计一条每一步都是简单可验证的工作流引擎，这应该是我们 loop 设计的一个目标。所以我们要设计的不是一个全能的 AI 大脑，不是通过 loop 去实现一个全能 AI 大脑，而是要通过 Loop 去实现一个高度的质量可控，然后契约简单可验证的。一套轻量化的运行时环境。那我们以 AIOps 的场景来举例。在智能运维的场景下，我们的全链路大概分成了五个阶段。

01:57:17

然后这五个阶段里面还有一个，就 是每个阶段之间可能有个小的闭环。举例来说，比如说我的一个要去做个 运维诊断或者一个变更的这个方案，在校验方案的时候，发现了问题，那么我们会回到方案生成阶段，重新闭环去校验，去生成一个准确的方案。然后每个阶段之间，我们会通过一个文件总线把它们串起来。文件总线，我们在这里给它一个形象的比喻，它形成一种窄腰型的设计。

01:57:49

也就是说，在每个阶段和阶段之间的交接必须非常简洁，有个非常简洁描述的契约，它是一个文件。根据这个文件我们会去验收。如果上一阶段通过了我的验收，我的状态机就继续往下推进。如果没有通过我的验收，我们就通过这个闭环，重新回到上一轮，再来一遍。这个就是我们智能体的 Loop 方案。

好，我们有了这个企业增强架构设计，这个架构设计到底有没有效？我们肯定还是需要有一个智能体的质量评估体系，对吧？那么智能体的质量评估体系和我们传统意义上的软件工程质量评估体系有什么不同呢？它的不同点就在于，智能体的质量评估体系更看重的是覆盖率和执行的完成度。这句话听着好像有点多余，难道我们传统的软件工程不去看覆盖度或者不去看这个执行度吗？也看，但是它对于覆盖度和执行度的强调，没有智能体质量评估这个场景下强调得这么高，或者强调得这么重要。

01:59:03

关于智能体的质量评估，刚才我的同事已经介绍了很多，在这里我不过多赘述，我就讲两点。智能体的质量评估在覆盖率上来讲，首先我们要保证智能体在我们设计的模型、Agent 运行时的环境，以及用例上，我们要保证 100% 覆盖，这是我们质量安全护栏的第一道。完成了覆盖度的校验以后，接下来我们会看它的执行完成，就检测执行是不是 100% 完成。然后在 100% 完成的基础之上，它的测试用例通过率是不是能达到我们的预期要求，比如说 95%。

01:59:48

然后它的一些 forbidden，就是严格红线的 case，是不是全部通过等等，以及对应的这些，像 Skill 的一些，比如说它的 Skill 调用率，在不同正反例案例下，它的调用是否符合我们的预期等等。那么这个就是智能体评估。

我们到底要拿这些数据怎么来实现自进化？在这一块，我们将自进化总结成六个闭环，分别是观测数据、生成轨迹，然后去挖掘知识，沉淀经验，将知识召回，最后去做验证。这六个闭环，前面我们刚才已经讲过了，包括观测数据，还有形成轨迹，这个刚才已经讲过了。在这里我们重点讲一下这个经验，我们怎么去挖掘知识，怎么去沉淀经验。这里我可以给大家直接讲一下我们的实践经验。

02:05:25

经验是什么？我们的经验其实就是一些结构化的数据和非结构化的数据。结构化的数据就是我们可以固定确定下来的一些东西。比如说我们执行这个任务，大概会调用到哪些工具，这些工具的执行的一个顺序大概是什么样的。那么这些东西可以用结构化的 YAML 文件来表示。还有一些非结构化的经验，比如说我们的执行规程。它是一个文档描述，类似于说一个 SOP。这些东西我们可以把它转换成对应的 Skill，或者把它转化成 RAG 里面的知识库。

02:05:58

这些都是一些非结构化的知识。那么经验就是这些东西，大概分为五大类，这个我就不一一念了，大家可以从 PPT 里面看到。接下来还有一个问题，就是我们沉淀了这些结构化和非结构化的知识，我们什么时候运用到我们的 Agent 现在环境？这里面其实有四个阶段。第一个阶段，任务开始阶段，也就是我前面跟大家分享过的，在输入层那个阶段，我们去做决策干预，它的效果是最好的。

02:06:33

所以这是我们注入经验知识的一个最好的阶段，就是任务开始阶段。接下来是工具调用前。工具调用前是指，我们在工具的调用过程中，因为模型之前的幻觉可能会造成它做大量的重试，产生耗时，产生无端的 Token 消耗。那么在工具调用之前，把我们的经验注入到上下文当中，能节省大量无端的成本消耗。第三个时机就是在我们的 Agent 执行步骤过程中报错的时候，我们可以通过知识图谱去加载对应的解决方案，然后去解决报错的问题。

02:07:15

最后一个阶段，就是在我们准备交付任务的时候，这个任务交付是指，你给我们的 Agent 下发一个任务，它执行完了，它把这个任务结果交付给用户之前，把我们的交付验证经验注入到上下文中，让它再去做一轮校验。这就是四个注入我们经验的最好阶段。整个 Agent 自进化的过程，其实我们也还是在不停尝试的过程中，我们也在不停地摸索，然后去学习。
