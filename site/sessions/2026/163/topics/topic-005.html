OpenAgent 真实云管理评测：可观测证据、用例资产与发布门禁

01:26:25 — 01:43:15 · 刘群

刘群以独立主题介绍 OpenAgent 在真实云管理场景中的端到端评测。报告从业务目标、复杂依赖、动态环境和安全要求确定评测目标，构建有版本管理、风险分级、黄金用例和 holdout 保留集的评测资产；再基于 trace 同时检查安全、任务完成、声明忠实度、过程正确性、真实资源状态及效率成本。创建数据库的实例说明结果成功仍可能存在无证据声明与重复工具调用，最后将横向比较和持续自动评测接入 CI/CD 发布门禁。

  • Agent是模型、提示词、Skills、工具、知识与运行环境组成的整体，需要真实业务端到端评测
  • 从客户工单、领域专家、知识库与对抗样本构建用例，脱敏验证后版本化入库
  • 以FMEA风险维度分级，黄金用例支撑回归与门禁；未公开的holdout保留集用于黑盒评测，避免针对用例集做过拟合优化
  • 先观测后评测；用回复声明和工具证据检查忠实度，并回查真实资源状态
  • 安全合规是一票否决红线，结果分、过程规范与Token/时延成本需要共同评估
  • 横向评测帮助选模型和改进用例，持续CI/CD门禁要求黄金用例通过并满足历史质量基线

幻灯片 05

OpenAgent 评测目标

01:28:43 — 01:31:10 官网回放 ↗
刘群
01:28:44

那么先做评测呢，第一件 事情是要明确评测的目标。要明确评测目标，先要对我们评测对象，也就是我们的 Agent，它的问题域和业务目标做全面的分析。我们构建的不是一个开放的、通用的评测基准，而是面向 OpenAgent 专用的评测体系。所以，那简单介绍一下 OpenAgent，刚才也提到了，OpenAgent 是阿里云推出的用于 智能云管理的一个 Agent 产品。

01:29:18

那么云管理这个业务有什么特点呢？它有四个鲜明的特点。第一，业务目标明确，就 是用户在云管理的过程中，他的任务目标是很明确的，比如创建个数据库。排查一次故障等等，能够客观的验证和衡量的。第二个，云管理业务往往比较复 杂，资源多，这个操作步骤也多，资源之间的依赖关系也很多，所以第三个特点是环境动态。那么云环境，它的资源在增减，状态在变化，所以它不是一个静态的快照。

01:30:01

最后一个是安全性要求很高，因为客户把自己的业务放在云上，你就必须做好安全的保障，比如租户 隔离、权限隔离、高危操作保护等等。那么基于云管理业务的这些特点，我们就可以定出评测的目标是什么。那么我们 OpenAgent 的评测目标也定了四个，第一个是真实环境中运行，我们把 Agent 和 Agent 触发的云管操作都放到真实的环境中去。让结果可验证，不做 mock。

01:30:36

第二个是多场景覆盖。我们需要有丰富且分布合理 的用例，然后做到多层次、多类别的覆盖。还有一个，这也是最重要的一个，就是多维度评估，既看结果也看过程。然后为 Agent 提供四个方 面，效果、效率、成本、安全方面的洞察。最后一个是评测驱动开发。要把我们的评测纳入到 Agent 开发的 CI/CD 流程中去。让评测与发布的质量挂钩。

幻灯片 06

用例集设计

01:31:10 — 01:34:01 官网回放 ↗
刘群
01:31:10

那么先看一下我们用例集的设计。因为这个也很重要。为了达到用例丰富和分布合理这个要求，我们先从场景分类中开始设计。就是我们的这个 Agent 它会面向哪些场景？我们不仅要覆盖各种云服务，这是 OpenAgent 的场景目标。我们不仅要覆盖它各种云服务的核心功能，也要覆盖跨账号、跨产品的复杂场景。还有，特别是安全方面的场景也要覆盖。那么这是我们有了这些场景范围之 后，我们就好定我们的用例范围了。

01:31:53

那么我们从四个来源来收集我们的用例。第一个呢是线上工单，占 60%， 这是客户真实的问题，价值最高。那么 30% 呢是由我们的业务领域专 家构造，还有 5% 基于知识库生成，还有 5% 的专门的对抗样本。专门的用于安全测试。那么这些初始的用例数据， 需要经过一条带版本管理的入库流程，才能转换为正式的用例。包括脱敏，提取事实和目标 API，然后做可行性验证，再最后经过人工 review，最终入库并更新版本。

01:32:36

这是一套带版本化流程。用例多了，因为用例其实很好造的。但是用例多了之后，就有一个问题，需要对它们的优先级进行分级。我们这边参考的是 FMEA 的 风险优先级的分类方法，由发生概率、严重程度加上检测难度三个维度来对用例进行分级。那么发生概率就是这个用例场景在客户侧真实出现的频率。比如说他每天都要运维操作的一些任务，那优先级肯定最高。还有一个呢是严重程度，就是 这个任务涉及到了资源变更，它能造成的影响程度和工单等级。

01:33:19

比如删除操作，它的这个等级就比较高。还有个是检测难度，就是发生错 误的时候，它被检查出来的难度。基于这三者相乘，我们把用例划分出了 P0、 P1、 P2 三个等级。把各个场景的 P0 级别的用例组合在 一起，就构成了我们的黄金用例集。那这个黄金用例集呢，非常重要，用于我们的线上回归和发布门禁。我们还特别构建了一套 holdout 保留集，用于黑盒评测。

01:33:53

黑盒评测，它是不公开的用例集。避免我们的 Agent 针对 用例集做过拟合的优化。

那这个来看一个具体的用 例示例啊，我们使用一套有确定 Schema 的 JSON 格式来 表达一个用例啊，比如说这个，这是“帮我在杭州创建一台 PostgreSQL 数据库”，还有按量付费等等要求，规格选最便宜的这样的要求，那这个是一个明确的用例输入。线上客户也确实会问这样的问题，给这样的任务。那么定义的用例的输入，还要定义它啊允许 调用的 API 范围和不允许调用的 API 范围，这些约束。

01:34:39

还有这些，因为创建数据库是付费操作，所以在用例中还强调了应该要唤起 Human-in-the-loop 确认。然后我们的定义中还支持定义一些脚本函数，来对用例执行过程中和最终 结果做这个确定性的校验。还有个值得一提的，就是用例跑着跑着其实也会跑飞的，会失控的。所以我们还要特别去约束 Judge LLM 的运行限制，它的最大轮数，最大的工具调用次数，还有超时时间等等。

01:35:10

正是因为有了这一套形式化的、确定性的结构，让我们的评测，让我们的用例成为了机器可运行、可验证的评测资产。这个资产很重要，它是后面自动化评测的基础。

幻灯片 08

评测维度和方法

01:35:27 — 01:38:28 官网回放 ↗
刘群
01:35:27

好，有了用例之后，我们来看一下怎么评。当然先评之前呢，我先强调 一个关键点，先观测后评测。没有足够的可观测数据是没有办法做评价的。那么 Agent 的 loop，我们的 OpenAgent 用的是阿里云的 Agent Loop 这个可观测服务。可观测服务完整的记录了我们的 trace 数据。如果同学们对可观测服务有感兴趣 的话，本届云栖大会也有专门的主题分享，这里就不展开了。

01:36:01

有了观测数据之后，我们主要看 Agent 的行为、Agent 行为结果六个方面，就是六个维度。第一个是安全合规，这是最重要的，它是红线，一旦违反，一票否决，直接 0 分。安全合规方面，我们主要看它在用例跑完之后，在 trace 中是不是出现了刚才不允许的调用。有没有暴露一些敏感信息。还有这个该唤起人工确认的时候，有没 有唤起人工确认，这些都要做到检查。

01:36:37

还有一些我们用 Judge LLM 做的策略判定。这是安全合规。第二个是任务完成度，这个 检查的是 Agent 的回复，Agent 的回复跟用户意图之间的匹配程度。我们看的是关键词召回，还有Judge LLM 的一个判断。当然这个 Agent 的回复，有时候看起来是正确的，但可能什么它都没干，只是幻觉出了一个恰巧的回复。那这个肯定是不够的，所以还得看它的忠实度。

01:37:11

忠实度我们是怎么计算的呢？我们用 Judge LLM 把 Agent 的回复拆分成一条条独立声明，然后再把这些声明去工具 调用结果中去找证据支撑。有支撑的就算一个，所以看这 个比例来得到它忠实度的评分。第四个看的是事实一致性。这个看的是它执行过程中是不是调用的是我们允许的 API，以及它的调用 参数，以及是不是符合我们的预期。还有过程正确性，事实一致性，刚才说的是过程正确性，事实一致性指的是这个。

01:37:50

任务结束之后，是不是真的发生了实际的效果？资源创建出来了没有？状态是不是符合预期的？最后一个是效率成本。这个主要包括端到端的延迟，还有对话轮数、Token 消耗这些成本和效率方面的指标。除了安全合规是一票否决制， 0 分的话，其他的维度呢，我们会计算出一个 100 分制的得 分，然后在各个维度再加权算一个总分出来，这样以一种直观的方 式来反映我们 Agent 的水平。
