幻灯片 03

企业级 Agent 的三项要求：工程化、规模化、组织化

01:10:18 — 01:11:35 官网回放 ↗
周琦
01:10:18

Agent进入企业要同时满足3项要求，第一项要求是工程化，传统软件是由程序预先定义的执行逻辑，Agent则会在运行过程中规划下一步的行动，新的工程体系需要把模型的概率性决策和程序的规则约束结合起来，既保留动态规划的能力，又让每一步遵守权限和业务规则。失败后能够恢复，结果又能够验证。第二是规模化，Agent的执行与等待交替发生，有时密集地调用工具，有时等待模型返回，也有可能等待人的审批。

01:11:01

任务需要保持持续，但计算资源可以按阶段安排，这直接影响着整个的运行效率和可承接的业务规模。第三是组织化，一个业务目标往往需要多个角色协作分工。在整个过程中，授权、人工确认和结果的验收往往都需要明确责任。整个过程执行的经验也需要能够留在企业里。

幻灯片 04

Agent 全生命周期：任务交付与能力积累

01:11:35 — 01:13:16 官网回放 ↗
周琦
01:11:35

因此，我们能够看到这三项要求要贯穿Agent从构建、运行到持续改进的全部过程。那我们从这张图，可以对照整个企业的管理来理解整个过程。一个团队在开始工作前往往需要培训和授权，在执行时需要分工协作，完成后需要复盘改进。成熟的方法需要通过标准化的方式推广出去。那我们回看Agent，也需要整个完整的过程。首先是构建和准入，我们需要把模型、工具和Skills组织起来，明确它能承担什么样的任务，然后组织和交付，让Agent在具体的流程中协作，把结果交给业务验收。

01:12:25

接下来是测评和进化，我们根据执行的记录和反馈找到问题，调整模型、上下文以及技能，再确认这个调整是否有效。最后，我们需要把验证通过的Agent、Skills和测评集沉淀下来，供下一次任务复用。这里最关键的是，业务交付产生的结果、验证后形成的资产、运行时的日志，都需要经过评测和筛选，才能成为值得复用的企业能力。同时，身份、权限、安全、成本、版本、责任要贯穿整个过程，要把这套生命周期的体系真正运转起来。

01:13:10

因此，整个云也需要围绕Agent的工作方式提供支撑。

幻灯片 06

Agent Sandbox： Agent Native Cloud 的新一代算力底座

01:14:06 — 01:15:55 官网回放 ↗
周琦
01:14:07

Agent要完成任务，需要真正地运行代码、操作浏览器、访问文件。Agent Sandbox就是承接这些行动的算力底座。这一页，我们提供了3种使用方式。第一种，Agent Sandbox提供了一个预置的环境，我们能够把依赖的Skills和模板准备好，让长会话的Agent能够在这个环境里面稳定持续地工作。那第二种方式，我们可以提供执行工具，通过代码解释器、浏览器和桌面等环境，把Agent的计划落实为具体的操作。

01:14:44

那第三种模式，企业也可以通过Agent Sandbox去扩展自己的执行环境，我们可以通过自定义模板连接VPC，挂载云存储，把Agent接到企业原有的这个资源体系中。支撑这3种方式，底层需要统一地管理模板、沙箱的生命周期、会话状态、文件卷和网络策略。例如，当一个任务执行到一半，接下来可能需要审批。那我们希望保持它的工作状态，在合适的时候能够休眠、唤醒，继续推进任务。

01:15:23

同时，我们也需要去减少整个等待时间周期的资源占用。那作为开发者，一方面可以通过熟悉的E2B API快速接入。那熟悉Kubernetes API的团队，也能够通过同样的方式进行管理和治理。这样，执行环境就能够根据任务按需准备、受控运行，并支持状态的恢复。再往环境内部去看，操作系统也需要适应这样的Agent的新负载。

幻灯片 07

操作系统：全新升级为 Agentic OS

01:15:55 — 01:17:33 官网回放 ↗
周琦
01:15:56

Agent的工作方式，对于操作系统也提出了新的要求。它会频繁地调用命令行，反复执行短任务，还可能启动多个子Agent，执行路径也会因为整个模型的判断不停地变化。因此，系统优化需要同时考虑交互的效率、运行的密度和执行的安全。在交互侧，让系统输出更适合Agent理解，减少无效信息和反复的尝试。那通过不断地去观察Tools和整个工具的调用，我们把给模型的上下文做了有效压缩，降低了整个Token的消耗。

01:16:45

那么在运行侧，我们通过内存和内核的优化，更高效地承接了大量的任务。在安全和恢复侧，能够通过eBPF的方式，让高危的动作能够被拦截，执行的过程能够被观测，工作区的状态可以回退。例如，我们在这个页面里面展示的数万文件的工作区回滚，在我们这个Agentic OS中，可以做到50毫秒之内。那对于需要不断尝试和修正的任务，这类能力可以极大地降低整个恢复的开销。

01:17:22

有了执行环境和系统的支撑，下一步就是需要去连接真实的云资源和企业的服务，让Agent的行动能够进入业务世界。

幻灯片 08

开放平台：业务意图的受控执行

01:17:33 — 01:18:47 官网回放 ↗
周琦
01:17:33

那当用户提出一个业务目标，比如说盘点资源、执行规划或者排查云上的风险，Agent需要把这个目标转化成一系列可执行的动作。那开放平台承载的就是这样的一个连接，在入口侧OpenAgent能够通过理解的方式去掌握用户的意图，组织方案和操作。在能力侧，我们通过API、通过MCP以及Skill的方式，把云产品和工具开放给Agent使用。在整个执行的过程中，身份、权限、动作的检验和审计必须到位。

01:18:15

需要审批的动作，要把决定权交回给人。那执行之后，我们同样需要追溯到是谁，基于什么样的权限，完成了什么样的操作。所以开放能力的价值体现在业务意图能够沿着一条受控的路径转化为真实的资源操作。当我们把这些工具和技能连接在一起，企业还需要去构建Agent，把多个Agent组织成一个团队，这就引出了AgentCore。

幻灯片 09

AgentCore：组织任务交付，沉淀企业能力

01:18:47 — 01:20:17 官网回放 ↗
周琦
01:18:47

那回到我们刚才提到的一条主线，一边我们需要去交付任务，另外一侧我们需要去积累能力。那AgentCore就把这两件事情连接在一起。首先，企业可以把Agent的定义、Skills、工作流以及知识和评测的基准作为有负责人、有版本、有权限的资产进行管理。当任务到来之后，平台组织Agent进行分工协作，在必要的环节引入人的审批和验收。在执行过程中，我们可以通过Harness协调上下文、模型、工具和运行资源，让任务在权限、预算和边界内能够持续地运行。

01:19:33

当任务结束之后，结果、执行轨迹和业务的反馈会再次进入评测和改进的流程里。我们据此调整模型、上下文和Skills，经过回归验证，再把有效的改进更新到企业的资产中。那通过这个流程，当企业每完成一次任务，就有机会为下一次积累一份经过验证的能力。身份、成本、版本和审计则会贯穿整个过程，这也让Agent的组织化有了具体的落点。团队里有哪些能力？如何协作？

01:20:11

结果由谁来验收？改进如何复用？都可以被有序地管理在一起。

幻灯片 13

Agentic Harness：任务执行控制与质量验收

01:21:31 — 01:22:50 官网回放 ↗
周琦
01:21:32

那我们最后来看一下Harness。Harness，我们可以理解为围绕任务执行构建的一套控制的这个体系。那Harness里面的话呢，它需要回答4个问题，任务使用什么样的模型和上下文，Agent以谁的身份调用哪些工具，任务中断之后如何恢复，预算如何控制，最后结果是否能达到验收的标准。那这4个问题的话呢，把模型、身份、资源和质量都连接在一起。授权要检查到具体的动作，成本需要落实到具体的任务，执行记录也需要同时能够支持测评和责任的追溯。

01:22:15

在这里我想强调一个衡量的标准，单位合格任务的成本。面对一个企业的工作流，我们需要把投入的资源与通过验收的这个业务任务放在一起看，才能去判断一次优化是否真正创造了价值。验收的标准越清楚，模型的选择、工具的编排和资源的调度越有共同的优化方向。最后，我们使用客户满帮的一张架构图来看一看，咱们前面提到的这些能力是怎么进入一条完整的执行链路。

沿着这张图，我们可以从左往右看。首先的话呢，一个成熟的系统必定是一个异步化的系统，人或者业务会提出他的这个目标，明确审批和验收的这个要求。那这类任务的话呢，会通过消息和会话的路由进入AgentCore的Runtime。那在这里，用户基于AgentScope构建的Agent组织上下文、规划协作和最后完成执行。运行的环境会提供会话保持、弹性运行和身份的接入。
