刚才确实听到很多客户、嘉宾的演讲，看到很多系统用在PolarDB上，首先感谢大家对PolarDB的信任。先自我介绍，我是翁宁龙，来自阿里云智能集团数据库产品事业部的。今天带来的主题分享是PolarDB的产品，叫PolarDB Agent Squad，从数据驱动的多智能体协作到企业研发的可靠交付。PolarDB整体战略里，Agent不只是辅助编程工具，要解决的是，当企业把复杂任务交给AI时，任务能不能稳定走到验收，执行过程能不能被治理，经验和数据能不能沉淀下来，持续复用。

01:40:50

过去一年，Coding Agent确实让很多人眼前一亮，单点任务确实提效了，但真正把Agent放到企业生产流程后，会发现几个问题，首先端到端交付可靠性，走到验收比较难，因为可能遇到，上下文依赖状态容易断裂，跨环节协作部分，分工、交接、结果汇总不明确。结果验证部分，AI输出缺少独立校验，往往会有失败恢复过程，过程不可控，难从断点恢复，往往需要人工的介入。

01:41:58

一旦流程需要人工介入，或者端到端交付需要人之间沟通协作，就会拉长整体交付周期。第二，个人提效很难转变为组织产能，包括企业能力集成，内部系统、数据、知识很难统一沉淀，系统接口、数据往往非常分散。第二个，场景质量一致性交付，今天用这个模型，明天用那个，或者今天用这套系统、那套系统，结果交付质量把控不一致，包括输入与规则差异、影响交付质量的部分，也是变量。再是AI对效能结果的评估，包括效率、质量、成本，它的口径是不一致的。

01:42:49

最后前面也讲到，AI最重要的是底层数据，数据与治理部分，包括权限、过程证据，还是比较难沉淀和追溯的。所以企业级Agent化，不能只关注单个Agent强不强，模型强不强，而是建立统一的任务和交付管理。统一管理任务流程、验收、数据沉淀和运行记录，这是PolarDB Agent Squad要解决的核心问题。

企业研发交付Agent化不是一蹴而就，归纳为5个逐步深入的阶段，从左边第一个开始，第一个阶段，Knowledge and Data Engineering，理解知识和数据，当然，有些企业用得比较浅，AI或者Agent使用还停留在这个阶段，理解知识、总结，帮你写周报、生成PPT，可能都在这个阶段。第二个阶段是Harness Engineering，做受控执行，会引入，第三个阶段是Agent Loop，基于环境工程持续完成任务。

01:44:06

第四个阶段是Loop Engineering，处理失败、恢复和自进化。第五个阶段，是目前PolarDB Agent Squad可达到的Agent System Engineering，组织协作和交付。特别说明，这五个阶段不是严格的瀑布，真实落地过程中会有回环和并行，排成递进，是说明企业级可交付需要逐步补齐的5类能力，也是与标杆客户，后面会有相应案例，共建中反复验证的路径。

PolarDB Agent Squad本身是什么呢？一句话总结，它连接企业业务系统、数据资产和场景工具，是任务编排和交付控制面。企业入口很多，需求平台、IM业务平台、工作台、API，Webhook，定时任务，这些都是企业的入口。PolarDB Agent Squad把这些入口统一成一条以交付为主线的任务。围绕一条任务，PolarDB Agent Squad管理五个维度。

01:46:25

首先是任务定义，做什么任务，包括目标、范围、输入输出的验收标准，这是最关键的一环。叫磨刀不误砍柴工。如果任务输入和验收标准只在脑子里，只在认知里，能不能告诉它？不能告诉AI，后面整个验收和统一会比较难。第二，流程编排，设置阶段、角色分工、状态和异常处理。第三，验收和证据，规则校验和人工复核，包括结果和过程数据留档。第四，数据和知识复用；第五，效能观测，包括周期、人工介入、质量和Token消耗，都是可观测部分。

01:47:17

最终所有运行、验收和审计数据回流到PolarDB数据底座，这是与竞品最关键的差异之一。不只是Agent执行，而是对企业整个交付结果负责，并让企业能力持续沉淀。

接下来看任务在PolarDB Agent Squad里怎么跑完，总结为4个闭环环节，首先明确需求，包括需求目标、范围，写清验收标准。第二，执行任务，按Playbook分工，在受控环境处理。第三，检验复核，按业务规则检查复核，记录结果问题；最后，验收交付，核对结果和验收标准，提交结果和交付记录。中间可能涉及3个异常环节，第一，检查不通过，那一定要带着具体的问题返修。

01:48:19

第二，运行异常，包括保留任务状态，按策略重试、恢复。出现范围变化、超出预算或反复失败时，暂停交由人处理。这个肯定越少越好。流程闭环一定做到检查有依据、失败有去处、交付有记录。这是PolarDB Agent Squad让复杂任务可交付的核心机制。

为了把交付经验复制到不同场景，都做了哪些事情？把它抽象成一套场景工作流，有统一任务契约，每个工作场景包括4个部分，首先业务上下文，里面有业务规则、知识库、历史记录，需要按需检索。第二，工具标准，Skill、MCP、CLI统一输入输出。第三，流程规则，包括Playbook、状态、重试、回退、接管规则。最后，验收标准，包括规则校验、复核等。结果只有这四种状态，Pass、Retry、Rewind和Human。

01:49:26

最重要的交互记录、交付证据沉淀到PolarDB数据底座啊，全程可追溯。意味着同一个任务、场景，反复执行时，都有统一标准和统一质量出口。统一质量出口包括可验收结果、相同标准和可追溯证据。整个过程、工具使用、决策是什么样，都是可追溯证据，以及可比较度量，包括完成率、周期、成本，都是可比较度量。以下列举不同业务场景验收口径，与很多标杆客户合作，沉淀下来的一些经验。

01:50:11

比如数据标注场景抽检一致性、设计评估场景规则覆盖，材料审核的一些核验的准确性，以及流程运营的周期与介入。

02:07:06
