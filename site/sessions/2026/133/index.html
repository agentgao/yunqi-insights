我们整体的思路其实分3层，就是AI Ready的数据底座。大家看这个词可能会比较陌生，但实际上是什么呢？实际上就是说，企业的数据很多都是存量的，我们如何把这些数据源和各种数据变成Agent可用的数据源。中间一层抽象出来很简单，其实就是说这些数据源只有写这些数据和弄这些表的人比较熟悉。业务的语义未必跟这个数据源直接对齐，比如今天想要销售额，那是订单结算的金额，还是我们合同的金额，还是说算上退款还是不算上退款，对吧？

00:05:31

每个企业的理解都不一样。中间的语义是结合数据库的语义，再加上企业的一些最佳实践文档，和大家需要的一个定义。对齐的口径到底应该用什么口径，对吧？然后以及在不同的场景和不同的需求的情况下，大家采集数据的可能方式和理解也不太一样。最上层是我们的Agent服务，我们有一些直接开箱即用的预装Agent，也会有一些比如预测、诊断等等的Agent。然后在这些基础上呢，过去其实你就是查数据，所以需要一个传统Data Agent去查数据库就可以了。

00:06:10

00:06:49

因为涉及到很多复杂的业务逻辑，需要跟企业的数据和很多工具做深度结合。我们推出了FDE，通过深入客户团队的交付团队，帮用户真正集成到他们现有的系统里面，让这个系统本身可以比较好地接入大家真正的生产环境，同时结果可验收。最重要的是什么呢？最重要的是不断推进复杂场景的落地，同时企业系统不是大家可能日常外部的一个Agent，为什么我们叫Data Agent as a Service？

00:07:30

第一，要把Context做好，举个例子，做业务研发时，最核心的是什么？就是底层的数据结构，就表结构怎么设计。Context也一样，需要做好资产分类，每一类资产有自己对应的职责。第一类资产叫记忆Memory。Memory属于Agent私有，也属于个人私有，必须有隐私性。它来自Agent，就是跟Agent对话，或任务执行过程中逐渐产生。这里面的东西带有概率性，可能不一定稳定。

01:12:14

01:12:50

01:41:58

01:42:49

最后前面也讲到，AI最重要的是底层数据，数据与治理部分，包括权限、过程证据，还是比较难沉淀和追溯的。所以企业级Agent化，不能只关注单个Agent强不强，模型强不强，而是建立统一的任务和交付管理。统一管理任务流程、验收、数据沉淀和运行记录，这是PolarDB Agent Squad要解决的核心问题。

PolarDB Agent Squad本身是什么呢？一句话总结，它连接企业业务系统、数据资产和场景工具，是任务编排和交付控制面。企业入口很多，需求平台、IM业务平台、工作台、API，Webhook，定时任务，这些都是企业的入口。PolarDB Agent Squad把这些入口统一成一条以交付为主线的任务。围绕一条任务，PolarDB Agent Squad管理五个维度。

01:46:25

首先是任务定义，做什么任务，包括目标、范围、输入输出的验收标准，这是最关键的一环。叫磨刀不误砍柴工。如果任务输入和验收标准只在脑子里，只在认知里，能不能告诉它？不能告诉AI，后面整个验收和统一会比较难。第二，流程编排，设置阶段、角色分工、状态和异常处理。第三，验收和证据，规则校验和人工复核，包括结果和过程数据留档。第四，数据和知识复用；第五，效能观测，包括周期、人工介入、质量和Token消耗，都是可观测部分。

01:47:17

最终所有运行、验收和审计数据回流到PolarDB数据底座，这是与竞品最关键的差异之一。不只是Agent执行，而是对企业整个交付结果负责，并让企业能力持续沉淀。

接下来看任务在PolarDB Agent Squad里怎么跑完，总结为4个闭环环节，首先明确需求，包括需求目标、范围，写清验收标准。第二，执行任务，按Playbook分工，在受控环境处理。第三，检验复核，按业务规则检查复核，记录结果问题；最后，验收交付，核对结果和验收标准，提交结果和交付记录。中间可能涉及3个异常环节，第一，检查不通过，那一定要带着具体的问题返修。

01:48:19
