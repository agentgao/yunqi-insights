# 分析与证据

## 按目的组织结果

| 用户目的 | 有用的结果 | 需要核对的正文 |
|---|---|---|
| 找感兴趣的话题 | 推荐主题、为何相关、适合谁、先读哪里 | 各候选 topic 的实际讨论与重点段落 |
| 快速了解一场 | 核心论点、议题结构、主要结论、关键限定 | 该场全部讲稿，包括开闭场 |
| 理解技术方案 | 问题、架构、组成、运行流程、取舍、适用场景 | 相关完整 topic 与涉及的前后章节 |
| 比较产品或路线 | 同一维度的差异、各自前提、证据和未披露项 | 每个方案的实际表述；不把未提及当作不支持 |
| 看趋势或共识 | 多场次的共识、分歧、变化线索、推断边界 | 广泛检索后阅读全文；保留独立 session 归属 |
| 提炼实践建议 | 可行动事项、依赖条件、待验证问题 | 演讲中的实践和限制；建议本身标为分析 |
| 写专题报告或分享材料 | 面向受众的论述结构与逐项证据 | 涉及的全部相关章节；标出未覆盖范围 |

根据问题选择合适结构。技术术语、英文原名、数字及其口径应能够回溯到段落，不通过不带出处的“常识补全”填补演讲未说的内容。

推荐项、比较表列名、段落说明和引用均以真实场次名称为主，例如“技术主论坛·Agentic Cloud”；需要定位时才附“[230]”。用户只给编号时也先查询名称。topic 同样使用主题名称，不让 `topic-002` 替代可读标题。内部编号用于检索与证据追踪，展示证据时须关联对应的场次名称。

讲者按已有可靠姓名展示，不追加花名、昵称或声音推断的称呼。讲稿中的原始称呼与展示姓名分别处理，不能将未确认的自报称呼合并成“正式姓名（花名）”。

## 从命中到结论

1. 利用 catalog 中的标题和摘要确定候选范围，再扩展近义词、缩写和中英文拼写检索正文。
2. 阅读完整命中段落和前后段。需要总结一个 topic 时继续读完其所有分页；结论跨章节时分别阅读全文。
3. 记录事实、讲者判断、案例、数字、限制条件和待确认词，不把编辑的画面标题视为独立一手表述。
4. 综合时对齐相同问题与口径。例如同样讨论“推理效率”，但首 Token 延迟、总体吞吐、成本和 SLO 是不同维度。
5. 对每个关键结论保留出处；形成新判断时解释它如何从已有证据得到，而不是让引用仅作装饰。

## 引用记录

需要提供详细出处时，可以使用：

```text
结论或问题：……
性质：原话 / 转述 / 分析推断
场次：技术主论坛·Agentic Cloud [230]
主题：AI Native：云基础设施的创新与发展 [topic-002]
段落：p000123
时间：00:18:12–00:18:47（原视频时间）
链接：https://yunqi.aliyun.com/2026/session?agendaId=230
支持段落：完整原文或精确短引文
限定条件与疑点：……
```

这里的段落 ID 和时间只是格式示例。实际段落、时间、讲者和 ID 必须从工具返回或内嵌全文读取，不能照抄示例。简短回答可以精简引用形式，保留场次名称和足以找回证据的时间信息。

视频引用使用 catalog 的 `official_url`。不构造 CDN 地址、播放凭证、本地路径或未经验证的跳转片段；官网页面有链接也不代表某场已经有可用回放。
